## Architecture decisions frozen for execution

- Build a TypeScript modular monolith: one React/Vite SPA, one NestJS API, and
  one PostgreSQL database in an npm-workspaces monorepo.
- Pin Node.js `24.18.0` LTS in development and CI, use the matching Node 24
  production container line, and pin `npm@11.9.0` through the root
  `packageManager` field. Do not use the local EOL Node `v25.6.1` as the baseline.
- Keep domain rules in `packages/domain`, transport schemas and inferred types
  in `packages/contracts`, and feature modules in each app. Controllers must not
  write lifecycle status fields directly.
- Choose Google OAuth as the MVP's one authentication method. Persist opaque,
  hashed server sessions and issue an `HttpOnly` cookie; do not place access
  tokens in browser storage.
- Use explicit focus-session segments from the start. They are needed for
  pause/resume/wait accounting and reliable daily-review metrics.
- Use HTTP for commands and SSE for server-to-client invalidation events. The
  client always refetches authoritative state after an event or reconnect.
- Do not add Redis/BullMQ initially. Add a durable database-backed AI-request
  status and a single-process scheduler first; reconsider a queue only after
  real reliability or throughput evidence.
- The first LLM adapter may use OpenAI's Responses API, but all feature code
  depends on an internal `LlmProvider` interface. Structured suggestions use
  Zod schemas, strict structured outputs, refusal handling, and application-side
  semantic validation. No model call may mutate task state directly.
- Keep the MVP to the deterministic execution loop first. AI, proactive
  behavior, notifications, and deployment hardening land only after that loop
  passes integration and browser tests.

## Product and architecture gaps resolved by this plan

- `MVP.md:100-120` leaves the auth method open. Google OAuth is selected to
  avoid building and operating email delivery for the first release.
- `MVP.md:970-988` calls session segments optional. They are required here
  because accurate focus time is an explicit MVP analytic.
- `MVP.md:180-192` mentions converting inbox items into notes, but the data
  model and feature boundary define no Note entity. Note conversion is deferred;
  a user can archive the item or preserve text in a task description.
- `MVP.md:939-968` lists projects and task dependencies while `MVP.md:1355-1374`
  excludes advanced projects and complex dependencies. The MVP keeps only an
  optional lightweight project label; dependency graphs are deferred.
- The weekly review endpoint at `MVP.md:1052-1060` is deferred. The inclusion
  boundary requires a daily outcome summary, while week planning is explicitly
  Phase 4.

## Findings considered and rejected

- Microservices: explicitly contrary to `MVP.md:22-61` and premature for a
  single-user execution loop.
- Redis/BullMQ in the first milestone: optional in the spec and unnecessary
  before durable asynchronous work or multiple API replicas are demonstrated.
- WebSockets: the required real-time traffic is server-to-client invalidation;
  SSE plus normal HTTP is enough.
- Event sourcing: the event table is audit/history data; PostgreSQL current-state
  rows remain authoritative.
- A general chatbot, embeddings, vector search, autonomous mutations, teams,
  calendar/email integrations, recurring tasks, and native mobile apps: all are
  explicitly outside the MVP boundary.
- A shared `packages/ui` package at bootstrap: there are no repeated components
  yet. Extract it only after the web app reveals a stable reusable surface.

## Global release gates

Before calling the MVP ready for a private pilot, all of these must pass from a
clean checkout with documented environment variables:

```bash
npm ci
npm run db:validate
npm run lint
npm run typecheck
npm test
npm run test:integration
npm run build
npm run test:e2e
```

The pilot must also demonstrate the full deterministic loop without an LLM key:
capture → process → plan → start → pause/wait/resume → capture distraction →
complete or stop → close day → view review.
